Vouch × Bright Data Scraper Studio

How we work with the scraper API

Bright Data's Scraper Studio can repair its own scrapers. Vouch is the layer that checks whether the repair still means the same thing — before it is committed. This page is the integration, end to end, as the code actually does it.

Why this is possible at all

The approval gate hands back rows, not just a diff

Everything downstream depends on this one behaviour.

Run scraper heal without --auto-approve and it exits 0 with an envelope containing status: "awaiting_approval" and preview_result — the sample rows the repaired scraper would return.

Scraper Studio's own Accept / Decline screen shows only the code diff. preview_result is surfaced by the CLI and API path alone. So Vouch validates data that Bright Data's own approval screen cannot show a human — and it does it before anything is committed, which matters because there is no programmatic rollback of an approved heal. The gate is the only safe place to stand.

We never pass --auto-approve. It commits without the gate, which removes the thing this product is.

The loop

One cycle, start to finish

Steps 1–2 happen once per collector. Steps 3–6 are the cycle that runs on a schedule, and the guardian sits between the proposal and the commit.

01 · ONCE
Create
A custom collector from a URL and a plain-English field description. Returns the c_* id.
scraper create <url> "<desc>"
→
02 · ONCE
Baseline
First clean run is profiled and stored. This becomes the yardstick every later heal is judged against.
scraper run <id> --sync
→
03 · CYCLE
Run
Routine scrape. If nulls spike or a field vanishes, the run is degraded and a heal is triggered.
scraper run <id> --sync
→
04 · CYCLE
Heal → gate ⏸
Bright Data proposes a repair and stops. We read preview_result.
scraper heal <id> "<prompt>"
05 · CYCLE — VOUCH
Judge 🛡
9 checks over the preview rows vs the baseline profile → a confidence score and a plain-English brief. No network call.
run_all_checks() → decide()
→
06a · PASS
Approve
Commit the repair. Same collector id, nothing downstream touched. Baseline advances to the verified rows.
scraper approve <id>
or
06b · FAIL
Reject & re-prompt
Scraper left unchanged. The guardian's own diagnosis becomes the next heal prompt. Capped at 2 attempts.
scraper approve <id> --reject
The re-prompt is the part worth watching. On a rejection, _resharpen_prompt() dispatches on the failing check and interpolates its evidence, so the validator writes Scraper Studio's next instruction — e.g. “the values you returned (median $16.75) match the shipping column's historical range, not price's (median ~$1,274.50)”. The baseline only ever advances on a heal the guardian confirmed; a rejected run never becomes the new yardstick.

The guardian

Nine checks, cheapest first

Pure stdlib, no network, no third-party deps — so the deterministic tiers gate whether the expensive LLM tier ever runs at all.

TierCheckSeverityFires when
1 · structuralFIELD_MISSINGcriticalA baseline field is gone
1 · structuralNULL_SPIKEhighEmpty rate rose > 20 points
1 · structuralROW_COUNT_SHIFTmediumRow count moved > ±50%
2 · distributionNUMERIC_DRIFThighA median moved > 50%
2 · distributionCARDINALITY_COLLAPSEmedium≥10 distinct values → ≤10% of that
2 · distributionBOOL_RATIO_SHIFTmediumTrue-rate moved > 50 points
2b · swapCOLUMN_SWAPcriticalValues sit on another field's distribution
2c · invariantVALUE_ORDER_INVERTEDcriticalprice > original_price on >20% of rows
2d · the pastREFERENCE_PRICE_UNSUPPORTEDlowA was-price exceeds what we confirmed pre-sale
3 · semanticLLM judgereview onlyConsulted only when tiers 1–2 return REVIEW

Scoring, then the decision

# one penalty per ROOT CAUSE, not per finding
critical 60  high 25  medium 10  low 3

if any critical or score < 60:  FAIL
elif any high  or score < 85:  REVIEW
else:                            PASS

A single critical fails regardless of score — a column swap cannot be outvoted by everything else looking fine.

Why swaps are charged once

One price↔shipping swap trips four checks: COLUMN_SWAP from both sides plus NUMERIC_DRIFT on both fields. Charged individually that is 170 points, which saturates the score to 0/100 — and a saturated zero reads as a broken meter, not as calibrated judgment.

So scoring collapses swap pairs to one charge and suppresses the drift as a consequence. Result: 40/100 — still a definite fail, but a legible one. Every finding is still reported; only the scoring collapses.

The trap that shaped the design

preview_result is a sample, and the docs never say how big

Every example in Bright Data's docs elides the array with …. Measured against our live collector: 1 row, against a 96-row baseline.

Any check that reasons about volume measures the preview instead of the heal: 

ROW_COUNT_SHIFT       Row count changed from 96 to 1.
CARDINALITY_COLLAPSE  'name' went from 96 to 1

Both are artefacts of the sample size — the heal itself was fine. So run_all_checks(is_sample=True) stands those two down, and HealProposal.is_sample carries the distinction from the real gate (always a sample) versus a fixture (full size).

Detection survives on one row

a legitimate pricePASS 100
shipping cost in priceFAIL 40
a null priceREVIEW 75
no price fieldFAIL 40
crossed-out original (14% high)FAIL 40

Three are row-local facts; COLUMN_SWAP asks which distribution a value sits on, not how it is spread. Only _profile_distance needed adjusting — below 5 rows it compares medians only.

What the verdict is for

One verification layer, two consumers

The verdict is the product; repricing is only its first consumer. The second one only exists because the first one works.

Example ① · the seller loses

Competitive repricing

The competitor relaid out their tiles, extraction broke, and the heal began reading the delivery cost into price. A normal repricer matches that phantom number and destroys the margin.

Finding
COLUMN_SWAP
Verdict
FAIL 40/100 — repair refused

Example ② · the shopper loses

Sale price audit

The retailer relaid out for a sale, extraction broke, and the heal repaired it correctly — which is what makes the new was-price checkable at all. Every price really fell; the number it is measured from was never charged.

Finding
REFERENCE_PRICE_UNSUPPORTED
Verdict
PASS 97/100 — repair committed
Exposed
−$1,469.99 overstated
The asymmetry is the argument. In ① the extraction was wrong, so the repair was refused. In ② the extraction was right, and that is precisely what lets us contradict the retailer. A guardian that only ever rejects is a filter; one that can also certify is infrastructure. And the second check is only trustworthy because of the first — you cannot audit someone's claim about the past if your own record of it might be corrupt.

Consuming it yourself

The verdict as a stateless endpoint

POST /verify runs the same pipeline with no product, no baseline row, no pricing and no writes. It takes no database session because it touches nothing. 

# judge candidate rows against a known-good reference
curl -X POST http://localhost:8000/verify \
  -H 'Content-Type: application/json' \
  -d '{
    "candidate_records": [{"name":"...","price":16.75,"shipping":1274.50}],
    "baseline_records":  [{"name":"...","price":1274.50,"shipping":16.75}],
    "is_sample": true
  }'

→ {
    "decision": "fail",  "confidence": 40,  "confirmed": false,
    "brief": "Rejected this heal. 'price' now matches the baseline
              distribution of 'shipping', not 'price'.",
    "failures": [{ "code": "COLUMN_SWAP", "severity": "critical", … }]
  }

Reference, either shape

baseline_records (raw rows we profile) or baseline_profiles (precomputed). Exactly one — both or neither is a 422.

Auditing a sale

reference_prices maps product → price confirmed before the sale. Omit it and that check stands down entirely.

Hardened

5,000-row caps, extra="forbid" so a typo'd knob errors instead of silently no-opping, inferred baseline_count.

Learned the hard way

Traps in the live API

Each of these cost us credits or left junk on the account.

TrapWhat happens, and what we do
description capped at 500 charsOver the limit returns 400 — and the collector still exists, because create provisions the template before starting AI generation. MAX_DESCRIPTION_CHARS validates locally so the call never leaves the machine.
AI generation takes 5–10 minPass a generous timeout (we default 900s). A shorter wall-clock cap loses the collector id from stdout while the job keeps running server-side.
No delete, no listThe CLI surface is exactly create / run / heal / approve. Every failed create leaves an orphan to remove by hand at brightdata.com/cp/scrapers.
Collector disabled after approveImmediately post-approval, run and trigger both return 403 Collector disabled. Re-enable from the dashboard; there is no programmatic toggle.
AI-Flow caps concurrency at 3A 4th concurrent create/heal returns 429. Our sweep is deliberately serial — fanning out would spend the demo in backoff.
Two env var namesCLI reads BRIGHTDATA_API_KEY; the Python SDK reads BRIGHTDATA_API_TOKEN. Config carries both.
npx on WindowsIt is a .cmd shim, so a bare name raises FileNotFoundError. Resolved with shutil.which — deliberately not shell=True, which would put a heal prompt through shell quoting.
--url on heal is cosmeticThe request body is {"prompt":…, "custom_input":[]}. Harmless to pass; do not build logic on it.
